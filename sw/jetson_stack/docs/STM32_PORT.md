# STM32N6570-DK Real-Board Port — the plan we worked from

> **Status: historical.** This was our porting plan while the board was still on the
> bench. The port is finished: the firmware in [`sw/guardian_vision/`](../../guardian_vision/)
> runs μT-Kernel 3.0 on the STM32N6570-DK and is measured in
> [`sw/docs/test_report.md`](../../docs/test_report.md). For the wiring as built see
> [`hw/wiring.md`](../../../hw/wiring.md), and for the build see
> [`sw/docs/setup_guide.md`](../../docs/setup_guide.md). Kept because it records why each
> choice was made.

> **Updated 2026-09-13**: Final check of the actual wiring — the Jetson is wired
> directly to the STM32N6570-DK Arduino connector **D0/D1 (USART2, PF6/PD5)**
> through a USB-to-TTL adapter (physical connection, voltage and driver all
> verified; see "Verified" below). Therefore **UART is the adopted path**, and
> `gatekeeper/stm32/gatekeeper_uart_bridge.c` is the bridge code that goes onto
> the real board. The Ethernet/lwIP path written earlier (`gatekeeper_lwip_udp.c`)
> remains valid, separately from network devices such as the Hokuyo lidar, but
> UART is fixed as the primary connection for the STM32 gatekeeper itself.

`gatekeeper/src/{protocol,safety_envelope,gatekeeper_core}.c` is pure C (C11)
with no references to HAL/CMSIS at all, so it goes into the real-board project
**unchanged**. The role that `gatekeeper/sim/main_sim.c` (Linux PTY) plays —
"byte stream → STX sync → 15-byte frame assembly → call gk_core_process → send
response" — is taken over on the real board by
`gatekeeper/stm32/gatekeeper_uart_bridge.c` (HAL UART interrupts + DWT cycle
counter). The logic is completely identical; only the transport layer differs.

## Verified (physical wiring)

| Item | Value |
|---|---|
| Jetson | USB-TTL adapter (PL2303 chip) → `/dev/ttyUSB0` |
| STM32 | Arduino connector D0 (=USART2_RX, PF6) / D1 (=USART2_TX, PD5) |
| Baud rate | 115200 8N1 |
| Kernel driver | This Jetson's kernel (5.15.148-tegra) does not include `pl2303.ko` by default, so it was built from the Linux v5.15 tag source (`toolchain/pl2303-build/`) — after a reboot you must start again from `insmod` (see below) |
| VESC | fw 6.6, v_in=15.1V confirmed (temporarily bench-connected to the Jetson as `/dev/ttyACM0` during testing). **Production wiring is STM32-only** — which USART to use is not yet decided (see 4b below) |
| Jetson lidar | Hokuyo UST-10LX, Ethernet `192.168.0.10:10940`, SCIP2.0 — verified with `jetson/ecu/lidar.py` |
| STM32 sensor | Not a lidar — uses the **STM32N6570-DK onboard camera + Neural-ART NPU** (`local_safety_monitor.c`, still a stub) |

Must be run after every reboot:
```bash
sudo modprobe usbserial
sudo insmod <repo on the Jetson>/toolchain/pl2303-build/pl2303.ko
sudo udevadm trigger
# verify with ls /dev/ttyUSB0
```
(To make it load automatically and permanently, it can also be registered in
`/etc/modules-load.d/` and
`/lib/modules/$(uname -r)/kernel/drivers/usb/serial/` — set up separately if needed)

## Why the real board cannot be built right now

The STM32N6 is a recently released chip, so:
- Register/clock/USART initialization code (CMSIS-Device headers, startup
  assembly, linker script) is normally generated by ST's STM32CubeMX/STM32CubeIDE;
  writing it by hand risks malfunction on a safety-critical board.
- Secure boot (attaching the FSBL signature header) requires
  **STM32CubeProgrammer**.
- ST distributes both for x86_64 only (no ARM64 support) → they cannot be
  installed on this Jetson (aarch64), so **this is done on an x86_64 desktop**.

## Procedure (desktop PC, assuming STM32CubeIDE is installed)

1. **Create the project with STM32CubeMX**: File → New → STM32 Project → select
   board `STM32N6570-DK`.
   - Connectivity → enable **USART2**, Mode: Asynchronous
   - Parameter Settings: Baud Rate `115200`, Word Length 8 Bits, Parity
     None, Stop Bits 1 (the defaults are already 8N1)
   - In the NVIC tab, confirm USART2 global interrupt is **Enabled** (required
     for HAL_UART_Receive_IT)
   - Use CubeMX's recommended defaults for Clock Configuration
   - Generate Code
2. Add the following 14 files as-is next to `Core/Src/` `Core/Inc/` of the
   generated project (they must compile unchanged — syntax checking with
   `gcc -fsyntax-only` against mock HAL headers already passes; an actual
   CubeIDE build has not been done yet):
   - `gatekeeper/src/protocol.c`, `safety_envelope.c`, `gatekeeper_core.c`
   - `gatekeeper/include/protocol.h`, `safety_envelope.h`, `gatekeeper_core.h`
   - `gatekeeper/stm32/gatekeeper_uart_bridge.c`, `gatekeeper_uart_bridge.h`
   - `gatekeeper/stm32/dwt_timing.c`, `dwt_timing.h`
   - `gatekeeper/stm32/vesc_uart.c`, `vesc_uart.h`
   - `gatekeeper/stm32/local_safety_monitor.c`, `local_safety_monitor.h`
     (collision-probability stub based on the STM32 onboard camera + NPU —
     always returns "safe"; once a real X-CUBE-AI model is integrated, only the
     inside of `local_safety_poll()` is replaced)
3. In `Core/Src/main.c`, add this on the line right after the
   `MX_USART2_UART_Init();` call (it must go inside a USER CODE block so CubeMX
   regeneration does not erase it):
   ```c
   #include "gatekeeper_uart_bridge.h"
   ...
   MX_USART2_UART_Init();
   gatekeeper_uart_init(&huart2);
   ```
4. In `Core/Src/stm32n6xx_it.c` (or the USER CODE callback area of main.c), add
   `HAL_UART_RxCpltCallback` if it does not exist yet and delegate to the bridge:
   ```c
   void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart) {
       gatekeeper_uart_rx_cplt_callback(huart);
   }
   ```
   (CubeMX may already have generated a weak default implementation of this
   function somewhere — in that case just add the one line above there)
4b. **VESC connection (separate USART, assumed value — must be confirmed in CubeMX)**:
   the VESC is connected only to the STM32, not to the Jetson (design decision —
   for the gatekeeper to hold final drive authority, there must be no path at all
   by which the Jetson can touch the actuators directly). Arduino D0/D1 are
   already used as USART2 for the Jetson link, and the STMod+ connector is
   electrically the same USART2, so it cannot be used for the VESC.

   **For now the code is completed with `USART3` as a provisional assumption**
   (which pins USART3 actually comes out on for this board is unverified — it
   is confirmed only by clicking D2/D3/D6/D7 etc. in the CubeMX Pinout view and
   checking the Alternate Function list). Once confirmed in CubeMX, enable USART3
   in the project, and if the generated handle is not named `huart3`, just adjust
   the name in the `main.c` snippet below
   — the logic code (`vesc_uart.c`) needs no changes.
4c. **`main.c` integration (full init block, copy-paste ready)**: after the
   CubeMX-generated `MX_USART2_UART_Init();` / `MX_USART3_UART_Init();` calls,
   add the following to the USER CODE block before the `while(1)` loop starts:
   ```c
   #include "gatekeeper_uart_bridge.h"
   #include "vesc_uart.h"
   /* USER CODE BEGIN 2 */
   vesc_uart_init(&huart3);        /* VESC only — a different UART from the Jetson link (huart2) */
   gatekeeper_uart_init(&huart2);  /* Jetson link; initializes DWT/gatekeeper state here */
   /* USER CODE END 2 */
   ```
   And the interrupt callback (in place of the weak function CubeMX generated, or
   newly added in `stm32n6xx_it.c`):
   ```c
   void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart) {
       gatekeeper_uart_rx_cplt_callback(huart);
   }
   ```
   `gatekeeper_periodic_safety_check()` must be hooked to a 50Hz periodic timer
   (TIM interrupt) — configure a TIMx at 50Hz in CubeMX, enable its interrupt, then:
   ```c
   void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim) {
       if (htim->Instance == TIM6 /* replace with the actual timer CubeMX assigned */) {
           gatekeeper_periodic_safety_check();
       }
   }
   ```
   (The timer number is also undecided — pick any free TIM in CubeMX and set it to 50Hz.)

5. Porting μT-Kernel 3.0 requires the official BSP2 from T-Engine Forum (license
   agreement required, cannot be downloaded automatically). Once ported, the
   init/callbacks from steps 3–4 just need to be wrapped in a μT-Kernel task
   (100Hz period) — `gk_core_process()` itself is reused as-is regardless of
   whether an OS is present.
6. Build → Run (ST-Link USB-C, desktop↔board). This is where it is actually flashed.
7. Set up the signed-boot pipeline with STM32CubeProgrammer (the FSBL signature
   header is the same concept as `sign_image()` in
   `jetson/threats/threat3_ota_tamper.py`, but the actual STM32N6 secure-boot
   header format must follow ST's documented specification).
8. After flashing, leave the USB-TTL cable in place (disconnect only the ST-Link
   USB used for flashing), and on the Jetson:
   ```bash
   ./jetson/scripts/run_vehicle.sh 15 --real
   ```

## What is verified now / what is not

- ✅ Safety logic (safety envelope, veto, replay defense, CRC) actually executed
  and verified with `gatekeeper_sim` — the code that goes onto the real board is
  already running.
- ✅ UART framing protocol measured on a real byte stream, albeit PTY-based.
- ✅ Jetson↔STM32 physical UART wiring and USB-TTL driver — verified.
- ✅ C port of the VESC protocol (`vesc_uart.c`) — CRC16 cross-checked
  byte-for-byte against the Python version, `COMM_SET_SERVO_POS` (id 12)
  encoding checked against the official vedderb/bldc firmware source. Syntax
  check against mock HAL headers passes.
- ❌ Actual response from the STM32 side — not yet (you mentioned a CubeIDE
  project exists, but these files have not yet been added to/built in that
  project; firmware not loaded).
- ❌ USART number for the VESC — `USART3` is an assumed value; must be confirmed with CubeMX.
- ❌ STM32 onboard camera + NPU collision-probability pipeline — CubeMX
  camera/ISP configuration and X-CUBE-AI model deployment do not exist yet.
  `local_safety_monitor.c` remains a stub that always returns "no obstacle"
  (the rest of the firmware still compiles and runs fully with this stub).
- ❌ Microsecond latency measurement on the real board (DWT counter, 600MHz clock) — not yet.
- ❌ Behavior under μT-Kernel 3.0 task scheduling — not yet (currently a pure
  HAL interrupt/polling bare-metal structure; μT-Kernel's real benefits, such
  as running the SafetyMonitor as a separate task, only appear after integration).
- ❌ Real secure-boot pipeline — concept only (Ed25519 demo), not the STM32N6-specific
  header format.

## How the open items above turned out

Every ❌ on this page was closed before the contest submission. This table is the map
from the plan to the finished work; the numbers all come from
[`sw/docs/test_report.md`](../../docs/test_report.md).

| Open item above | What was actually built |
|---|---|
| Response from the STM32 side; firmware not loaded | [`sw/guardian_vision/`](../../guardian_vision/) — a Makefile project on μT-Kernel 3.0 BSP2, flashed and running. Images in [`sw/binaries/`](../../binaries/) |
| USART number for the VESC was assumed | USART3 confirmed, and the RX/TX pins turned out to be **swapped** (A5 is input-only), at 38400 baud — [`hw/wiring.md`](../../../hw/wiring.md) |
| Camera + NPU pipeline does not exist; `local_safety_monitor.c` is a stub | Real pipeline: IMX335 → DCMIPP → YOLOX-nano INT8 on the Neural-ART NPU at 15 fps, person class, distance from box height. Runs as the `vision` task |
| No microsecond latency measurement on the real board | DWT cycle counter (1.25 ns) with a log-linear histogram in the firmware. Hazard → brake 34 µs max over 66 events; the full table is in the test report |
| Bare-metal structure, no μT-Kernel scheduling | Five tasks at fixed priorities — gate 8, imu 10, vision 20, report 25, log 30 — plus a dispatcher hook, an MPU view per task and a mutex with priority inheritance on the shared I2C bus |
| Secure boot is concept only | Out of scope for this submission. The board boots the ST FSBL from NOR flash and the signed application image; no custom root of trust was built |
